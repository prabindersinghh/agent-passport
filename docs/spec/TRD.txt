Agent Passport — Technical Requirements Document
TRD v0.1 | Reference architecture and implementation specification
1. Technical Objective
Build a runtime-independent policy and identity layer that can sit between an AI agent and the tools/resources it controls. The implementation must support agent-first and project-first provisioning, role-scoped agent shells, human approval gates, MCP integration, and OpenTelemetry-based tracing and run summaries.

5. Policy Evaluation Semantics
The effective permission for an action must be the intersection of all applicable restrictions. A higher-order deny must override an allow. Approval is not equivalent to allow; it is a pending state until a valid human approval exists.
Decision
Meaning
Execution
ALLOW
All applicable rules authorize the action
Execute
DENY
A deny rule or missing required authority blocks the action
Do not execute
APPROVAL_REQUIRED
Action is permitted only after explicit human approval
Pause and request approval
APPROVED
A valid approval exists for the exact scope/time requested
Execute
EXPIRED
Approval existed but is no longer valid
Do not execute; request again
Priority rule: DENY > APPROVAL_REQUIRED > ALLOW when the same scope conflicts, unless an explicit policy hierarchy says an even higher-level restriction applies.
6. Policy Composition
Organization Policy      +Project Policy      +Agent Passport      +Session constraints      =Effective Authority
Organization policy may establish non-overridable denies.
Project policy defines resource and workflow expectations for the repository/environment.
Agent Passport defines identity, declared role and delegated authority.
Session constraints may narrow scope temporarily.
An agent cannot use a lower layer to override a higher-order deny.
7. Agent-First Provisioning
agent-passport agent init --name coder
Generate stable agent ID.
Generate key/material for local signing or runtime authentication where configured.
Create passport.yaml with no implicit privileged capabilities.
Register optional runtime adapter metadata.
Return instructions to attach the agent to a project.
Do not infer production access or other high-risk authority from agent creation alone.
8. Project-First Provisioning
agent-passport init
Discover repository/project metadata.
Detect likely tools and execution surfaces.
Create project.yaml and policy.yaml.
Create default shell templates if requested.
Display a permission proposal with safe defaults.
Require human approval before activating non-trivial authority.

10. Four-Shell Architecture
.agent/agents/  researcher/passport.yaml  coder/passport.yaml  reviewer/passport.yaml  deployer/passport.yaml
Shells are identities plus policy scopes; prompts can describe behavior but do not provide authority.
A single LLM may switch between shell identities through an orchestration controller.
Role switch creates a new span and an explicit audit event.
Each shell may have separate memory namespace and context budget.
Cross-shell handoff should use signed or auditable artifacts rather than hidden conversational state where possible.
11. Orchestration Model
                Orchestrator                     |      +--------------+--------------+      |              |              | researcher       coder         reviewer      |              |              |      +--------------+--------------+                     |                  deployer                     |               human approval
The orchestrator decides sequencing and delegation. The Passport gateway decides whether the current shell is authorized to perform each requested action. This separates intelligence/planning from authority/enforcement.
12. MCP Enforcement
MCP is the first high-value integration surface because agent tool calls are explicit and structured. Implement an MCP gateway/proxy that resolves the active agent identity and resource context, evaluates the requested tool/action, emits telemetry, and only then forwards the call.
Agent  -> Passport MCP Gateway      -> identify agent + project + shell      -> evaluate policy      -> emit decision event      -> [approval if required]      -> forward tool call      -> capture result      -> emit outcome event

14. OpenTelemetry Design
Use OpenTelemetry to correlate agent intent, policy decisions and real execution. Keep high-cardinality content such as file bodies, prompt text and secrets out of default spans. Use IDs and references instead.

Security requirement: Never place raw credentials, API keys, full secrets or sensitive source content into telemetry attributes by default.

17. Memory Architecture
Memory is portable but should not be treated as the authority boundary. Store memory by agent/shell namespace and project scope. Authorization decisions must always come from policy state, not from recalled conversational context.
memory/  agents/    researcher/    coder/    reviewer/    deployer/  projects/    <project-id>/

19. Security Model
Least privilege by default.
Default deny for unknown or high-risk actions.
No self-escalation by agents.
Human approvals must be scoped, time-bound where appropriate, and auditable.
Policy changes are versioned and attributable to an authority.
Sensitive credentials remain in the underlying credential provider; Passport references authority rather than exposing secrets.
Telemetry must redact secrets and minimize sensitive content.
Tool adapters fail closed when policy evaluation is unavailable for protected actions.
20. Failure Modes
Failure
Expected Behavior
Policy engine unavailable
Fail closed for protected actions; allow only explicitly designated safe-local reads if policy permits.
Telemetry unavailable
Do not block safe local development by default, but mark run as telemetry-degraded; protected actions may require stronger fail-closed policy.
Approval service unavailable
Approval-required actions remain blocked.
Passport missing
Agent cannot operate in governed mode.
Policy malformed
Refuse activation and show validation errors.
Agent attempts privilege escalation
Deny and emit security event.
Runtime changes
Identity remains stable; runtime metadata is updated and revalidated.

24. Test Strategy
Unit test policy evaluation, precedence, scoping and approval semantics.
Golden-file tests for discovery-generated policies.
Adapter tests for MCP, filesystem and Git operations.
Adversarial tests where the agent attempts to exceed authority.
Replay tests: reconstruct a run summary solely from recorded events.
Cross-runtime tests: same Passport loaded by at least two agent adapters.
Failure-injection tests: policy service, telemetry and approval service outages.
Security tests for secret leakage in logs and telemetry.
25. Acceptance Criteria for v0.1
A developer can create an agent Passport without a project.
A developer can initialize a project and receive a conservative policy proposal.
A human can approve/edit permissions before activation.
A four-shell configuration can be created and each shell has distinct authority.
An unauthorized tool call is blocked before the underlying tool executes.
A human approval can be requested and recorded for a protected action.
A run summary can be generated without relying on LLM self-reporting.
OpenTelemetry traces correlate run -> role -> policy check -> tool call -> outcome.
An agent cannot elevate its own permission.
The system remains usable when the underlying LLM or runtime changes.
26. Key Architectural Principle
Agent Passport is not an instruction file attached to a model. It is an enforcement and accountability layer. The LLM provides planning and reasoning; the Passport provides identity and authority; the gateway mediates execution; OpenTelemetry provides traceability; the summary engine reports verified work.
